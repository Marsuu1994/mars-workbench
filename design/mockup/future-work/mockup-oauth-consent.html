When it shows

  • Supabase redirects to /oauth/consent?authorization_id=… and getAuthorizationDetails returns details (no prior consent).
  • Not signed in → the proxy sends you to /auth/login?next=… first and Google sign-in lands you back here.
  • Already consented → Supabase returns a redirect_url and the page redirects straight back; no UI.

Data mapping

  • Name: client.name. Tile: client.logo_uri, or the first letter when empty.
  • Email: user.email.
  • Return host: the host of redirect_uri. Client names are self-asserted under dynamic registration; the host is the part to trust.
  • Scopes: scope split on spaces, muted. The capability list is static copy: the token reaches every MCP tool whatever the scopes.

Actions

  • Allow / Deny → server action → Supabase approve/denyAuthorization → redirect to the returned redirect_url (Deny carries error=access_denied).
  • Switch account → sign out, then /auth/login?next= this page.

Layout

  • Chromeless (no sidebar or tab bar), same glow + grid as login, one 420px column. Mobile uses the same column with tighter padding.

Allowing…

  • Transient: from the click until the browser leaves for redirect_url.
  • The pressed button shows a spinner and "Allowing…" (or "Denying…"); both buttons are disabled so the decision can't be sent twice.
  • If the action fails (for example, the request expired while the page was open), the page re-renders into the invalid-link state.

When it shows

  • authorization_id is missing, or getAuthorizationDetails errors (unknown, expired, or already decided).
  • An approve or deny that fails lands here too.

Copy

  • Generic on purpose: the page can't tell expired from forged, and it doesn't know which client started the flow.
